The Problem

Railway apps are cluttered & untrustworthy

Most apps bury the one thing passengers actually want — where is my train right now? — under ticketing, PNR, ads, and plain text lists.

🧩Feature bloat

Ticketing, PNR, seat maps and ads crowd out the core live-tracking use case.

📄No spatial awareness

Location shown as textual lists instead of an intuitive, map-based view of the journey.

❓Fabricated data

Estimates are presented as fact — users can't tell a real GPS fix from a schedule guess.

The Solution

A map-first, truthful live companion

  • A map is the primary interface — search bar overlaid directly on a live route map.
  • Truthful telemetry: every position is tagged ACTUAL_GPS vs ESTIMATED_SCHEDULE — never synthesized.
  • One codebase delivers Android, iOS & Web parity via Expo + React Native Web.
  • Backend caching & coalescing protect upstream quotas and keep loads sub-second.
  • System-aware Dark / Light theming using official TrainPulse brand colors.

Core Features

What TrainPulse does

🔍Journey Search

Where-to-where search between any two stations with debounced autocomplete.

📡Live Telemetry

Status, speed, location, next halt, arrival/departure times and delay minutes.

🗺️Interactive Map

OpenStreetMap + Leaflet route map on Web & Mobile via WebView.

🚉Platform Status

Confirmed / Expected / Unavailable states with freshness timestamps.

🚃Coach & My Coach

Visual rake layout with a My Coach selector and offline persistence.

🛡️Zero Fabrication

Missing GPS is explicitly flagged, never invented.

Architecture

Decoupled client ↔ secure gateway

A zero-secret frontend talks only to the TrainPulse backend. Upstream credentials stay server-side.

📱 ClientExpo / RN Web + Zustand
→
⚙️ Hono Gateway/api/v1 · Zod validation
→
⚡ Cache + Coalescer30–45s TTL · single-flight
→
🛰️ RailRadarGPS telemetry (Bearer auth)

🔒Secret isolation

Client bundles contain no API keys — it doesn't even know RailRadar exists.

🤝Request coalescing

50 clients polling one train = 1 outbound request, broadcast to all.

♻️Graceful degradation

On 429/503, serve stale data with X-Cache: STALE + a freshness warning.

Principles

Security & design discipline

  • Zero-trust frontend: no third-party railway keys ever reach the client.
  • Error sanitization: auth headers, tokens & upstream keys redacted before logging or responding.
  • Truthful by default: approximations are labeled, GPS gaps are flagged — never faked.
  • Lifecycle-aware polling: pauses on background / hidden tab via AppState & visibilitychange.
  • Deliberately out of scope: no ticketing, PNR, seat availability or accounts — focus stays on tracking.
